# Idempotency

## 1. Overview

Idempotency is the property that applying an operation once or multiple times has the same effect on the system state. In practice, an idempotent API call means: you can safely retry it, replay it from a dead-letter queue, or receive it twice from a webhook — the result is the same as if you received it exactly once. Idempotency exists because distributed systems inevitably deliver messages more than once: message queues deliver at-least-once, network timeouts cause clients to resend, webhooks fire when they are not acknowledged within the provider's timeout, and background job schedulers retry failed jobs. Without idempotency, every retry is a latent data-corruption risk.

## 2. Core Principles

- **Idempotency is a property of the consumer, not the producer.** The producer may send a request once; the consumer must be able to see it 0 or N times and produce the same result. This is the core responsibility.
- **Safe retries require both an idempotency key and a unique constraint.** The key lets the producer say "these are the same request." The unique constraint on the consumer side ensures the database enforces it — if two nodes race, the DB rejects the duplicate.
- **HTTP methods have built-in idempotency.** `GET`, `PUT`, `HEAD`, `DELETE`, and `OPTIONS` are idempotent by specification (RFC 7231). `POST` is not — each call is defined to create a new resource.
- **Idempotency keys must be generated by the caller, not the callee.** If the server generates the key, two simultaneous requests with the same business intent will receive different keys and both succeed. Caller-generated keys ensure collision.
- **Webhook handlers MUST be idempotent.** Webhook providers retry on timeout. A handler that creates an order on every delivery will double-charge customers. The provider's SLA: "we retry for up to 3 days."
- **Eventual consistency is not a substitute for idempotency.** If the consumer stores a "processed" flag and retries are fast enough that the flag is set before the second arrival, that works — but only with a unique constraint as the safety net. Race conditions are the norm, not the exception.
- **The idempotency check must happen before any side effect.** Writing to the DB before checking the dedup store means a crashed process leaves a partially committed side effect.

## 3. Sub-Concepts

### 3.1 HTTP Method Semantics (GET, POST, PUT, DELETE, PATCH)

**Definition:** HTTP methods carry different idempotency guarantees by definition. `GET` and `DELETE` are idempotent: calling them 10 times has the same effect as once (a GET returns the same representation; a DELETE returns 404 on subsequent calls). `PUT` is idempotent: replacing a resource at a known URI is the same whether done once or multiple times. `POST` is NOT idempotent: each call creates a new subordinate resource. `PATCH` is ambiguous: RFC 5789 defines it as a partial update; if the patch document is idempotent (e.g., `{"set": {"status": "active"}}`) the result is idempotent, but if it's a sequence of instructions (`{"inc": 1}`) it is not.

**Why it matters:** Engineers who assume `PATCH` is idempotent because it looks like "a small PUT" will double-increment counters on retry.

**Scanner signals:** HTTP method strings in route definitions; `app.post` / `app.get` / `router.put` / `@patch` decorators; client call methods (`client.post` vs `client.put`).

### 3.2 Idempotency Keys (Format, Generation, Storage)

**Definition:** A unique token (usually a UUID v4 or a hash of business fields) generated by the caller and sent with the request. The consumer stores the key with the result of processing. On a second request with the same key, the consumer returns the stored result without re-processing.

**Why it matters:** Without a caller-generated key, the consumer cannot distinguish "retry of request A" from "new request B that happens to look similar." The key is the dedup mechanism.

**Implementation patterns:**
```python
# ✅ CORRECT — caller generates UUID key; consumer stores key→result mapping
import uuid

def create_order(items: list) -> Order:
    order_id = str(uuid.uuid4())  # idempotency key
    resp = requests.post(
        'https://orders.example.com/v1/orders',
        headers={'Idempotency-Key': order_id},
        json={'items': items},
    )
    return Order(**resp.json())
```

```python
# Consumer side: store idempotency key with result
def handle_create_order(request: Request) -> Response:
    key = request.headers.get('Idempotency-Key')
    if not key:
        return Response(status=400, body='Idempotency-Key header required')

    # Atomic check-and-write using a unique constraint
    try:
        with db.transaction() as tx:
            # Check if already processed
            existing = tx.execute(
                "SELECT response_code, response_body FROM idempotency_keys WHERE key = %s",
                (key,),
            ).fetchone()
            if existing:
                return Response(
                    status=existing['response_code'],
                    body=existing['response_body'],
                    headers={'X-Idempotent-Replay': 'true'},
                )

            # Process the request
            result = process_order(request.json())

            # Store result BEFORE returning (no race)
            tx.execute(
                "INSERT INTO idempotency_keys (key, response_code, response_body, created_at) "
                "VALUES (%s, %s, %s, now())",
                (key, 201, json.dumps(result.body)),
            )
            return Response(status=201, body=result.body)

    except UniqueViolation:
        # Another request with same key won the race — return their result
        existing = db.execute(
            "SELECT response_code, response_body FROM idempotency_keys WHERE key = %s",
            (key,),
        ).fetchone()
        return Response(
            status=existing['response_code'],
            body=existing['response_body'],
            headers={'X-Idempotent-Replay': 'true'},
        )
```

**Key format recommendations:**
- Use UUID v4 for caller-generated (cryptographically random, collision probability negligible).
- Use hash of business fields for derived keys: `sha256(f"{user_id}:{invoice_number}:charge")`.
- Include the intent: `charge:user:123:inv:456:v1`.
- TTL the key store: 24–72 hours for payment keys; 1–2 hours for API keys.

**Scanner signals:** `idempotency_key`, `Idempotency-Key`, `idempotencyKey`, `idempotency_keys` table, unique constraint on a key column, `X-Idempotent-Replay` header.

### 3.3 Unique Constraints as the Safety Net

**Definition:** A database-level unique constraint that enforces idempotency regardless of application-level race conditions. If two nodes race to process the same request, the DB rejects the second `INSERT`.

**Why it matters:** Application-level dedup ("if key not in cache, process") is racy in distributed systems. Two nodes can both see "not in cache" before either writes. The DB constraint is the only arbiter.

```sql
-- ✅ CORRECT — unique constraint on idempotency key
CREATE TABLE idempotency_keys (
    key             VARCHAR(255) PRIMARY KEY,
    response_code   INTEGER NOT NULL,
    response_body   JSONB NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_idempotency_keys_created_at ON idempotency_keys(created_at);
-- TTL: run daily cleanup for keys older than 72h
-- VACUUM or DELETE WHERE created_at < now() - interval '72 hours';
```

```python
# Even simpler: unique constraint on the business key itself
# For payments: one payment per (user_id, invoice_number, version)
CREATE TABLE payments (
    id              UUID PRIMARY KEY,
    user_id          UUID NOT NULL,
    invoice_number   VARCHAR(255) NOT NULL,
    amount_cents     INTEGER NOT NULL,
    status           VARCHAR(50) NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, invoice_number)
);
-- If two charge requests arrive for the same invoice:
-- INSERT fails with UniqueViolation → idempotent!
```

**Scanner signals:** `UNIQUE (` in SQL; `unique=True` in ORM field definitions; `UniqueConstraint` in Django/Peewee; `create_unique` in raw SQL.

### 3.4 Deduplication in Message Consumers

**Definition:** Because message queues deliver at-least-once, consumers must deduplicate messages. The dedup store is typically a DB table, Redis SET, or a compacted Kafka topic keyed by event ID.

**Why it matters:** Without consumer-side dedup, a redelivered payment event charges the user twice. Without a dedup store with TTL, the table grows unboundedly.

**Implementation patterns:**
```python
# Consumer: dedup before processing
PROCESSED_TTL = 72 * 3600  # 72 hours

async def handle_payment_event(event: dict):
    event_id = event['id']

    # Redis SETNX with TTL — fast, atomic
    was_new = redis.set(f'dedup:payment:{event_id}', '1', nx=True, ex=PROCESSED_TTL)
    if not was_new:
        logger.info(f'skipping duplicate event {event_id}')
        return  # already processed

    try:
        process_payment(event)
    except Exception:
        # Do NOT remove the dedup key on failure!
        # If we retry the same event, we want to re-process.
        # Solution: use a "processing" flag with a short TTL,
        # and only mark "processed" on success.
        raise
```
```go
// Go — dedup via DB unique constraint
func HandlePaymentEvent(ctx context.Context, event PaymentEvent) error {
    result, err := db.ExecContext(ctx,
        "INSERT INTO processed_events (event_id, processed_at) VALUES ($1, now())",
        event.ID,
    )
    if err != nil {
        if isUniqueViolation(err) {
            return nil // already processed
        }
        return err
    }
    if n, _ := result.RowsAffected(); n == 0 {
        return nil // duplicate
    }
    return processPayment(ctx, event)
}
```

**Scanner signals:** `processed_events` table; `dedup:` Redis key prefix; `setnx` usage; unique constraint on `event_id` in consumer DB; `compacted` on Kafka topic.

### 3.5 Webhook Delivery and Acknowledgment

**Definition:** A webhook is an HTTP callback from a third-party service (Stripe, GitHub, Twilio) to your server. The provider fires it and retries on non-2xx response. Your handler must acknowledge it (return 200) before doing heavy processing — or must process fast enough.

**Why it matters:** Stripe retries webhook delivery for up to 3 days with exponential backoff. A handler that creates the order before returning 200 is safe for the *provider*, but the processing can fail *after* the ack. A handler that does heavy processing before returning 200 will trigger retries on a timeout. Both scenarios require idempotency.

**Implementation patterns:**
```python
# ✅ CORRECT — webhook: enqueue for async processing, return 200 immediately
@app.route('/webhooks/stripe', methods=['POST'])
def stripe_webhook():
    event = stripe.Webhook.construct_event(
        request.data, request.headers.get('stripe-signature'), endpoint_secret
    )
    event_id = event['id']

    # Fast dedup check
    if redis.sismember('processed_stripe_events', event_id):
        return '', 200  # already seen

    # Enqueue for async processing
    sqs.send_message(
        QueueUrl=SQS_URL,
        MessageBody=json.dumps(event),
        MessageAttributes={
            'event_id': event_id,
        },
    )
    redis.sadd('processed_stripe_events', event_id)
    redis.expire('processed_stripe_events', 72 * 3600)
    return '', 200
```

**Common mistakes:** Processing synchronously before returning 200 (triggers provider retry on timeout); storing event ID only in Redis without a TTL (leaks); not verifying the webhook signature (anyone can POST fake events); accepting events out of order.

**Scanner signals:** `/webhook` / `/webhooks` route definitions, webhook signature verification (`stripe.Webhook.construct_event`, `github-webhook` verify), `processed_events` / `processed_stripe_events` dedup stores.

### 3.6 Payment and Financial Idempotency

**Definition:** In payment systems, idempotency is a correctness requirement, not a nice-to-have. A double-charge is a direct financial loss for the user and a liability for the platform.

**Why it matters:** Payment providers (Stripe, Adyen, Braintree) all require an idempotency key for every charge request. Their contracts: "send the same key twice and you get the same result." Your contract with your users is the same.

```python
# ✅ CORRECT — Stripe charge with idempotency key
import stripe
stripe.api_key = settings.STRIPE_SECRET_KEY

def charge_customer(customer_id: str, amount_cents: int, idempotency_key: str):
    try:
        charge = stripe.Charge.create(
            customer=customer_id,
            amount=amount_cents,
            currency='usd',
            idempotency_key=idempotency_key,  # Stripe's dedup key
        )
        return charge
    except stripe.error.StripeError as e:
        logger.error(f'charge failed: {e}')
        raise

# Key generation: deterministic from business context
def make_idempotency_key(user_id: str, invoice_id: str, attempt: int) -> str:
    return f"charge:{user_id}:{invoice_id}:v1"
```

**Scanner signals:** `idempotency_key` param passed to Stripe/Adyen SDK calls, unique constraint on `(user_id, invoice_number)` in payments table, `PaymentIntent` / `Charge` creation in financial code.

### 3.7 Eventual Consistency and Confirmed State

**Definition:** After processing an event, the consumer should confirm the state transition and make it visible to readers. The dedup key is part of the confirmed state — "event X was processed at time T with outcome Y."

**Why it matters:** If the processing result is not persisted atomically with the dedup check, a restart loses the "already processed" flag and the event is processed again.

**Scanner signals:** `processed_at` column alongside dedup key; atomic transaction that includes both the business write and the dedup record.

### 3.8 Idempotency at the API Gateway Level

**Definition:** API gateways (Kong, AWS API Gateway, Envoy, NGINX) can enforce idempotency at the edge, typically via an idempotency token header and a backend cache/db.

**Why it matters:** Placing idempotency at the gateway ensures it is enforced uniformly across all backend services, even those that don't implement their own dedup.

**Implementation patterns:** Envoy's `ext_authz` filter with an idempotency check; AWS API Gateway + DynamoDB for idempotency; Kong's `idempotency` plugin.

**Scanner signals:** Gateway config referencing idempotency, `X-Idempotency-Key` header validation in middleware, `ext_authz` with idempotency check.

## 5. Anti-Patterns

### Anti-Pattern: No Idempotency on POST / Write Endpoints

**Description:** A POST endpoint that creates a resource with no idempotency key and no unique constraint.

```python
# ❌ WRONG — POST with no dedup mechanism
@app.post('/orders')
def create_order(items: list):
    return db.insert('orders', {'items': items, 'status': 'pending'})
# If the caller retries on timeout, two orders are created.
```

**Why it's dangerous:** Every timeout → retry creates a duplicate. In a payment system this is double-charging. In an order system this is duplicate inventory. The most common production incident in distributed systems.

**Detection:** `POST` route without `idempotency_key` header handling and no unique constraint on the table being written.

**Fix:**
```python
# ✅ CORRECT
@app.post('/orders')
def create_order(items: list):
    key = request.headers.get('Idempotency-Key')
    if not key:
        abort(400, 'Idempotency-Key required')
    try:
        with db.transaction():
            existing = db.execute(
                "SELECT id FROM orders WHERE idempotency_key = %s", (key,)
            )
            if existing:
                return existing
            order = db.insert('orders', {'items': items, 'status': 'pending', 'idempotency_key': key})
            return order
    except UniqueViolation:
        return db.execute("SELECT * FROM orders WHERE idempotency_key = %s", (key,))
```

### Anti-Pattern: Webhook Without Dedup

**Description:** A webhook handler that processes the event but doesn't remember that it did.

```python
# ❌ WRONG
@app.post('/webhooks/stripe')
def stripe_webhook():
    event = stripe.Webhook.construct_event(...)
    process_charge(event['data']['object'])  # processes every time
    return '', 200
```

**Why it's dangerous:** Stripe retries on timeout. `process_charge` creates a new charge record on every delivery. A single Stripe event can result in N charges.

**Detection:** `/webhook` route without `processed_events` / `setnx` logic.

**Fix:** Store processed event IDs in Redis SET or DB with TTL. Check before processing.

### Anti-Pattern: Client Generates Idempotency Key Per Request

**Description:** The client calls `uuid.uuid4()` inside the function that makes the HTTP call, so every retry gets a new key.

```python
# ❌ WRONG
def create_order(items: list):
    key = str(uuid.uuid4())  # new key every call
    resp = client.post('/orders', headers={'Idempotency-Key': key}, json=items)
    return resp
# On retry: new key → server treats it as a new order.
```

**Why it's dangerous:** The whole point is to reuse the same key on retry. A per-request key makes dedup impossible.

**Detection:** `uuid.uuid4()` / `uuid4()` or `nanoid()` called in the same function scope as the HTTP client call.

**Fix:** Generate the key once at the application boundary (request handler, API client init) and pass it through.

### Anti-Pattern: Check Dedup Key AFTER Writing to DB

**Description:** The consumer processes the event, writes to the DB, and only then checks the dedup store.

```python
# ❌ WRONG
def handle_event(event):
    # Process first...
    db.insert('orders', event)
    # ...then check dedup
    if redis.get(f'dedup:{event['id']}"):
        return "already processed"
```

**Why it's dangerous:** Two identical events arriving simultaneously both process the event. The first one writes to DB; the second one writes a duplicate before either checks the dedup store. The unique constraint on the dedup table prevents this — but the business data may already be duplicated before the constraint fires.

**Detection:** AST: business DB write (insert/update) before dedup store check.

**Fix:** Check dedup FIRST. If duplicate, return immediately. Only process if not seen before.

### Anti-Pattern: No TTL on Dedup Store

**Description:** Dedup keys are stored forever.

```sql
-- ❌ WRONG
CREATE TABLE processed_events (
    event_id VARCHAR(255) PRIMARY KEY
    -- No TTL, no created_at, no expiry
);
```

**Why it's dangerous:** The table grows linearly with event volume. After months, it contains billions of rows. Queries slow down, disk fills, backups take hours.

**Detection:** `processed_events` table with no `created_at`, `expires_at`, or TTL policy.

**Fix:** Add `created_at TIMESTAMPTZ` and a daily cleanup job: `DELETE FROM processed_events WHERE created_at < now() - interval '72 hours'`. For Redis, use `SET key value EX 259200` (72 hours).

### Anti-Pattern: Blind Retry Without Checking for Idempotency

**Description:** The retry library retries every `Exception`, including `UniqueViolation`.

```python
# ❌ WRONG
@retry.retry(stop=stop_after_attempt(3))
def create_order(key):
    db.insert('orders', {'idempotency_key': key})  # will fail on retry
```

**Why it's dangerous:** The first call succeeds. The retry library catches the UniqueViolation from the second attempt and retries it again. The third attempt also fails. Wasted work.

**Detection:** Retry config that catches `Exception` / `BaseException` on a function that writes with a unique constraint.

**Fix:** Exclude `UniqueViolation` from retry exceptions. If the unique constraint fires, the request was already processed — return the existing result.

### Anti-Pattern: Non-Deterministic Idempotency Key

**Description:** The idempotency key depends on mutable state like timestamps.

```python
# ❌ WRONG
key = f"charge:{user_id}:{invoice_id}:{datetime.now().isoformat()}"
```

**Why it's dangerous:** The timestamp changes between the original call and the retry. The key is different. The server treats it as a new request.

**Fix:** Use only immutable business fields: user ID, invoice number, operation type. No timestamps.

## 7. Integration Points

- **Depends on:** A durable store for dedup keys (PostgreSQL, Redis, DynamoDB); `foundation.retries` for safe retry policies; `foundation.message-queues` for consumer dedup in queue consumers.
- **Used by:** Payment endpoints (Stripe, Adyen charge API), webhook handlers (Stripe, GitHub, Twilio), message queue consumers (Kafka, RabbitMQ), background job processors, API gateway plugins.
- **Related concepts:**
  - **`foundation.retries`:** Retries are the reason idempotency exists. Every retry without idempotency is a potential data corruption.
  - **`foundation.message-queues`:** Message queues deliver at-least-once. Consumer dedup is idempotency applied to async work.
  - **`foundation.cap-consistency`:** Idempotency is the practical implementation of "what does at-least-once delivery mean for my data model." The combination of unique constraints + dedup is the CAP trade-off: sacrificing availability for a few milliseconds to guarantee consistency.

## 9. Evolution / Version Tracking

**Early era (2000s):** Monolithic applications had no idempotency concern. The caller and callee shared memory and a transaction. Idempotency was implicit.

**SOA era (2010s):** As services split, engineers discovered that network failures and retries caused duplicate side effects. Payment providers (Braintree, Stripe) were the first to formalize idempotency as a contract requirement. "POST to /charges with the same idempotency key returns the same charge."

**Microservices era (2015+):** Webhooks became standard (GitHub, Stripe, Shopify, Twilio). Every webhook integration guide includes idempotency warnings. Event-driven architectures (Kafka, RabbitMQ) made at-least-once delivery the norm. Consumer dedup became a standard component of every event processor.

**Cloud-native era (2018+):** API gateways (Kong, Envoy, AWS API Gateway) added idempotency plugins. Redis became the standard dedup store due to O(1) SETNX and automatic TTL. Stripe's idempotency key contract became the industry template for financial APIs.

**Emerging patterns (2020s):**
- **Deterministic idempotency keys** from business context (hash of `user_id + invoice_id + operation`) replacing UUID generation — enables the caller to reconstruct the key from any context.
- **Idempotency in event sourcing** — the event stream IS the idempotency record. The consumer's last-processed offset is the idempotency check. Adding a unique constraint on `(stream_id, sequence_number)` in the projection table.
- **Webhook verification as idempotency gate** — signing the webhook (HMAC-SHA256) and verifying the signature ensures that only the legitimate provider can generate events, making dedup a secondary line of defense.
- **Compacted topics in Kafka** — using `log.cleanup.policy=compact` on a topic keyed by event ID. Kafka automatically deduplicates and retains the latest value for each key. This is idempotency at the broker level.
- **Standardization:** The IETF draft "Idempotency-Key HTTP Header Field" (draft-ietf-httpapi-idempotency-key-header) is making the `Idempotency-Key` header a formal HTTP standard.

**Deprecated patterns:** "Just retry and hope the DB unique constraint catches it" (without checking before writing); "idempotency is the framework's responsibility" (it is not); relying on `SELECT FOR UPDATE` locking for dedup (does not work across clusters).
